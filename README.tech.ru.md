## Профиль

Более 11 лет работаю с Linux-инфраструктурой. Занимаюсь эксплуатацией распределённых сервисов, выпусками, наблюдаемостью, сетью, хранилищами, разбором инцидентов и защитой рабочих контуров.

Пишу код там, где готового инструмента недостаточно: для диагностики, генерации конфигурации, сверки состояния, безопасного повтора операций и обработки научных данных. Это не отдельная специализация в серверной разработке, а часть работы DevOps/SRE-инженера.

## Избранные проекты и задачи

### [«Астросферум»](https://github.com/Haeniken/bot_astrosferum)

[Сайт проекта](https://astrosferum.com) · [ORCID 0009-0005-5804-5011](https://orcid.org/0009-0005-5804-5011)

«Астросферум» — разработанная мной система прогноза условий для астрономических наблюдений. Она загружает данные ICON-EU и ICON Global в GRIB2, проверяет полноту цикла, извлекает атмосферные поля и считает облачность, ветер, устойчивость, прозрачность и показатели астрономического качества. Каждый результат привязан к исходному циклу модели; графики для Telegram, VK и веб-интерфейса строятся из сохранённых расчётов.

В обычном прогнозе обрабатывается сокращённый вертикальный профиль. Режим «Горизонт» отдельно сравнивает восемь направлений на геометрической высоте 10°. Для каждого срока рассчитываются эфемериды, а итоговые графики явно отделяют расчёт по модели от наблюдений.

#### «Астрокупол»

Сейчас разрабатываю направленный прогноз по всему небосводу от 10° до зенита: 129 направлений на каждый из 72 почасовых сроков, всего 9 288 узло-часов. Для одного набора загружаются все 74 полных уровня ICON-EU, 75 полууровней геометрии и 19 приземных полей.

Исходные метеорологические величины восстанавливаются вдоль преломлённого луча. Только после этого считаются Cₙ², сиинг, атмосферное время когерентности τ₀, изопланатический угол θ₀, PWV, воздушная масса, облачная оптическая толща, туман, прозрачность и сдвиг ветра. Готовые индексы между узлами не интерполируются. Ошибка одной ячейки помечается отдельно и не отменяет остальные направления и сроки.

NASA GEOS-CF подключается как необязательный источник аэрозольных составляющих AOD и общего столба озона. Температура, давление, влажность и ветер по-прежнему берутся из ICON. Если данные NASA устарели или неполны, пропадает только дополнительная спектральная оценка, основной прогноз продолжает работать.

Расчётное ядро, очередь заданий, серверная авторизация и интерфейсы WebGL2/Canvas уже развёрнуты для контролируемой проверки. До публичного выпуска остаются измерения нагрузки, проверка обычного прогноза под той же нагрузкой и подбор коэффициентов по открытым данным DIMM обсерваторий.

### Отказоустойчивая сеть из семи узлов

Для небольшого рабочего контура внедрил полносвязную сеть с постоянными служебными адресами. WireGuard используется как основной транспорт, заранее поднятый IPsec/XFRM — как резерв, маршрут выбирает FRR через BGP и BFD. Входящие и исходящие списки префиксов разрешают только адрес конкретного узла.

Написал генератор конфигурации и ранбук: добавление узла без перенумерации существующих XFRM-интерфейсов, выпуск и поэтапная замена сертификатов, удаление скомпрометированного узла, диагностика и откат. Переключение периодически проверяю в действующем контуре: ограничиваю сбой одной парой, жду маршрут через IPsec, проверяю ICMP и прикладной запрос, затем подтверждаю возврат в WireGuard. Zabbix получает выбранный транспорт, состояние BGP/BFD, свежесть WireGuard и наличие IPsec SA без лавины зеркальных событий.

### GitOps для Traefik

В [GitOps Traefik Panel](https://github.com/Haeniken/gitops-traefik-panel) оператор добавляет домен через проверяемую процедуру. Панель нормализует Unicode/Punycode, проверяет A/AAAA, WHOIS и дубликаты, создаёт запрос на слияние в GitHub и показывает проверки, выкладку и выпуск TLS-сертификата. Изменение инфраструктуры остаётся в Git и проходит тот же путь, что ручной запрос на слияние.

### Согласование PostgreSQL и внешних систем

В закрытой панели управления разделил фиксацию платежа и применение желаемого состояния на нескольких внешних узлах. PostgreSQL хранит баланс, журнал операций, задания, аренды и поколения; сетевые вызовы выполняются после завершения транзакции. Повторное уведомление не зачисляет баланс второй раз, а временно недоступный узел обрабатывается повторно и затем сверяется с записанным состоянием. Для входящих уведомлений используются HMAC-проверка, непрозрачные метки и отдельный журнал аудита.

Отдельно пересмотрел границу между PostgreSQL и 3x-ui. Выдачу и продление доступа вынес из транзакций базы данных в задания с арендой, поколением операции и безопасным повтором. Фоновая сверка возвращает внешние узлы к записанному состоянию, а конфликт в 3x-ui не оставляет операцию навсегда зависшей. Подпись платёжного уведомления проверяется через HMAC-SHA256; повторная доставка и конфликты покрыты тестами.

### Архитектурный аудит семи узлов

Сверил фактическую конфигурацию семи работающих узлов перед выбором общей оркестрации. Контур состоял из самостоятельных установок Docker Compose: состояние было привязано к локальным ZFS-пулам и каталогам, очереди RabbitMQ разнесены по узлам, а наблюдаемость и резервное копирование частично зависели от одного сервера. Версии, способ сборки образов и сетевые правила тоже различались.

По итогам зафиксировал целевую схему: неизменяемые образы собираются в CI и загружаются из реестра, узлы получают явные роли, служебный трафик уходит в отдельную сеть, а состояние либо реплицируется, либо выносится из вычислительных служб. Для очередей предусмотрен общий отказоустойчивый кластер вместо нескольких независимых брокеров; для контейнеров — единые правила проверки работоспособности, журналирования, секретов и ограничений ресурсов.

Переносить весь контур в растянутый Docker Swarm не стал: локальные данные и разные границы отказа превратили бы кластер в общий источник риска. Первым кандидатом оставил только вычислительный сервис, но после удаления локального состояния, объединения очереди и проверки идемпотентности нескольких реплик.

### Производительность мониторинга

- **Производительность Zabbix и PostgreSQL/TimescaleDB.** Разложил задержку по физическим дискам, ZFS, системному RAID, PostgreSQL и ограничениям контейнеров. Логически раздельные нагрузки использовали одни HDD: `iowait` доходил до 86–90%, а один диск давал задержки 300–440 мс. Для текущего контура ограничил фоновый сбор, настроил PostgreSQL и ресурсы веб-интерфейса; долгосрочным решением определил отдельный SSD/NVMe для PostgreSQL и WAL вместо дальнейшей настройки общей группы HDD.
